Concurrency bug diagnosis:
- Old lock design: global exclusive section + TRAPEXIT cleanup that spun with forks (flock/ls/wc/touch every ~40ms per shell), causing fork storms → 'fork failed: resource temporarily unavailable', gum failing to spawn, high CPU on user's i3-10105F (4c/8t).

New lock design (agreed direction, implemented in lock.sh):
- fd-based flock semaphore: pre-create N lock files (default max=3, no nproc fork); _zshrc_sem_acquire tries slots 1..N with `flock -n`; if all busy, blocks once on slot 1 with `flock -w $timeout`; on timeout proceed unthrottled (return 1, `.zshrc` does `|| true`).
- Release = close fd (`exec {fd}>&-`); kernel auto-releases on crash; NO TRAPEXIT.
- _zshrc_with_lock wraps only actual file writers as functions in current shell (fd flock works in same shell, no -c subshell): compinit (zcompdump writer), history no-dups guard, mise completion, podman completion. Zinit clone guarded (race: two shells both see missing → both clone).
- Global exclusive section in .zshrc REMOVED; whole .zshrc sits under semaphore only to bound CPU.
- lock.sh must do zero external forks at source time (only define functions/typeset vars).

Testing constraints: max 5 shell startups allowed; prefer zsh -n syntax checks + non-interactive lock-only tests (source lock.sh, sleep 0.2) to keep CPU low; semaphore concurrency test with 3 procs holding 0.3s verifying max concurrency ≤ slots.
